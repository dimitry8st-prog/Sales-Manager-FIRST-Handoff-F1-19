INTEGRATION NOTE — F1-19
Техническая ревизия: R1
Ревизия передачи: R1
Проект: sales-manager-first

1. Компонент и зависимости

Файл: source/sales_handoff_intent.py

Публичный вызов:
build_handoff_intent(context, recipient, interest) -> dict

Прямая зависимость:
sales_first_handoff.assemble_handoff_context — принятый F1-09.
Файл sales_first_handoff.py остаётся неизменным.

Модуль подготавливает намерение передачи клиента.
Внешних действий, записи в БД и отправки уведомлений не выполняет.
Дополнительные зависимости и миграции БД не требуются.

2. Производитель данных

Точка будущего подключения:
sales_manager.process_notify_reply.

Вызывающий код получает подтверждённое решение классификатора,
полную историю, факты, материалы и доверенного получателя.

Ответ сохраняется через sales_store.record_reply.
Затем вызывается build_handoff_intent.

Порядок сохранения, транзакционные границы и восстановление
должны быть согласованы с контрактами общего приложения.

recipient.approval_ref и interest.evidence_ref проверяются
компонентом как идентификаторы. Подлинность подтверждений
и полномочия получателя обеспечивает вызывающий контур.

context.product_id формируется из явного доверенного
binding.offer_id. Не угадывать product_id по другим полям.

3. Вызов и обработка результата

intent = build_handoff_intent(
    context=context,
    recipient=recipient,
    interest=interest,
)

При status=HOLD:
- не создавать действие HANDOFF;
- не отправлять уведомление;
- сохранить причину INTEREST_NOT_CONFIRMED
  по правилам общего приложения.

При status=PREPARED:
- получить полный подготовленный context;
- преобразовать результат в HANDOFF ActionV1;
- передать действие принятому журналу;
- создать предусмотренную задачу через task_store.create_task
  по его опубликованному контракту и правилам идемпотентности.

Ошибки HandoffIntentError содержат публичный code:
INVALID_INPUT или SCOPE_MISMATCH.

Ошибки HandoffContextError из F1-09 передаются без подмены.
Ошибку нельзя трактовать как успешную передачу.

4. Преобразование в HANDOFF ActionV1

Опорный пример:
EXAMPLES.json, поле handoff_action_expected.

В ТЗ указан путь vectors/f119.json; в полученном пакете
буквальный пример действия находится в EXAMPLES.json.

Правила преобразования:
- schema_version: FIRST_ACTION_INTENT_V1;
- kind: HANDOFF;
- action_id: intent.handoff_id;
- event_id: context.handoff_event_id;
- scope: client_id, runtime_campaign_id, lead_id,
  mailbox_ref, thread_id из проверенного контекста;
- expected_state_revision: текущая подтверждённая
  ревизия состояния; значение 0 относится только к примеру;
- policy_version, locale и language_pack_version:
  из проверенного контекста;
- template_id: null;
- fact_ids: идентификаторы всех фактов полного context.facts;
- payload: recipient_ref, handoff_id, content_sha256
  и полный context из результата;
- binding_version: из доверенной привязки;
- payload_sha256: рассчитать по правилам канонизации
  общего контракта.

Не заменять payload_sha256 значением content_sha256:
они относятся к разным структурам данных.

5. Проверяемый пример вызова

Из корня исходного пакета, при доступном source в PYTHONPATH:

import json
from pathlib import Path
from sales_handoff_intent import build_handoff_intent

example = json.loads(
    Path("EXAMPLES.json").read_text(encoding="utf-8")
)
intent = build_handoff_intent(**example["input"])

assert intent == example["expected"]
assert intent["status"] == "PREPARED"
assert intent["context"]["delivery_status"] == "NOT_DISPATCHED"

Этот пример проверяет компонент.
Само преобразование в ActionV1 и вызов журнала
нужно проверить отдельно при интеграции.

6. Журнал, повторы и восстановление

Один handoff_id с тем же содержимым:
обработать по правилам повторов принятого журнала.

Тот же handoff_id с другим содержимым:
обработать как конфликт по контракту журнала.
Не перезаписывать прежнее действие молча.

Изменение content_sha256 при изменении содержимого
проверено собственным тестом.
Настоящий журнал и его обработка конфликтов не проверялись.

После сбоя сверить устойчивые состояния ответа, действия,
задачи и результата уведомления. Не отправлять повторно
только на основании повторного вызова build_handoff_intent.

Право владения человеком фиксируется после согласованного
устойчивого перехода. Реальную отправку выполняет отдельный
доверенный адаптер с подтверждением результата.

Лимит canonical payload нового адаптера журнала: 16 MiB.
При превышении отклонить действие, сохранив полный контекст.
Не обрезать историю, факты или материалы.

7. Границы компонента

PREPARED означает, что данные подготовлены.
NOT_DISPATCHED означает, что отправка не подтверждена.

Поле context.status=HANDED_OFF в подготовленном контексте
само по себе не доказывает фактический переход владения
или доставку уведомления.

Компонент не реализует классификатор, журнал,
уведомления и остановку кампании.

8. Незакрытые интеграционные проверки

NOT_RUN:
- соединение с настоящими производителями и потребителями;
- буквальное совпадение созданного ActionV1
  с handoff_action_expected;
- повторы и конфликт содержимого в принятом журнале;
- конкурентные изменения ревизии состояния;
- сбой сохранения и перезапуск между этапами;
- восстановление после неопределённого результата отправки;
- согласованный переход владения человеку;
- отклонение payload больше 16 MiB без обрезки;
- независимая итоговая проверка FG10.

Перед внедрением инженер сверяет текущую целевую SOURCE identity.
Внедрение выполняется отдельно с receipt/rollback
и независимой проверкой итоговой версии.
